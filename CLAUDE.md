# Рабочие договорённости по репозиторию kaggle-pro

Четыре соревновательные задачи: `01_moscow_flat_prices`, `02_company_bankruptcy`, `03_hospital_procurement_fraud`, `04_procurement_winner`. Работаем только в ветке `main`, коммиты сразу туда.

## Роли и порядок работы
- Пользователь — аудитор. Он решает, какие методы и данные допустимы. Реализация, варианты и деление на фазы и шаги — на Claude.
- Вопросы задаются в любой момент, в том числе пока считается код. Каждый вопрос явно выделен: кратко проблема, варианты, рекомендация.
- Обязательно выносить на обсуждение:
  1. методы, допустимость которых под вопросом;
  2. любой новый импорт в тетрадь, кроме исходных данных: данные из интернета, файлы из других тетрадей.
- Решения должны быть идейными, как у исследователя, а не перебором ради метрики. Цель — минимальная ошибка.

## Стратегия работы (скорость и корректность)
1. **Старт проекта, 10–15 минут.**
   - Быстрый EDA.
   - Adversarial validation (train против test): ловит сдвиг и ID-подобные признаки.
   - Выбор схемы фолдов по устройству test: GroupKFold по сущности (компания, тендер), временной сплит, если test идёт позже.
   - Baseline из 2–3 разнородных моделей.
2. **Общая обвязка `exp_lib.py` в scratchpad.**
   - Данные, фиксированные фолды, метрика, `cv()` → OOF.
   - Все агенты импортируют только её. Скор считается по сохранённому OOF, а не со слов агента.
3. **Параллельные агенты** (пример — Workflow `flat-prices-improve` в проекте 1). Одновременно: поиск в интернете по задаче, семейства признаков, разные модели.
   - У каждого агента явные границы («X не делай, это задача другого агента»), чтобы не дублировать работу.
   - Потоков в сумме не больше 4: при K агентах `n_jobs = 4 // K`. Для XGBoost и CatBoost число потоков задавать явно.
4. **Одна гипотеза — одно атомарное изменение** от текущего лучшего варианта. Так виден эффект каждой идеи.
5. **Скрининг дешёвой моделью.**
   - LightGBM: шаг 0.1, ~400 деревьев, `max_bin` 63.
   - Подвыборка 10–20% годится только для грубого отсева.
   - Подвыборки обманывают, где качество держится на группах (дома, компании) и групповых статистиках. Такие идеи и всех финалистов проверять на полной выборке с теми же фолдами.
6. **Правило принятия.**
   - Парный прирост по фолдам примерно больше 2 стандартных ошибок, знак совпадает минимум в 4 из 5 фолдов.
   - Финалистов перепроверять на втором seed разбиения. На малых данных — 3×5 repeated CV.
7. **Анти-утечка.**
   - Target encoding только вложенно внутри фолда.
   - Исторические признаки только по прошлому.
   - Перед финалом — отдельная проверка кода на утечки и автотесты сабмита: число строк, порядок Id, нет NaN.
8. **Порядок признаков.** Доменные (финансовые коэффициенты, цена/НМЦК, ранги внутри тендера) → групповые агрегации и частоты → взаимодействия.
9. **Тюнинг один раз**, после признаков: `num_leaves`, `min_data_in_leaf`, `feature_fraction`, регуляризация.
10. **Усреднение.** Модели разных семейств, таргетов и наборов признаков, плюс 3–5 seed. Состав смеси выбирается по OOF, веса равные.
11. **Финальная тетрадь.** Параметры зафиксированы, 4 потока, замер времени с запасом 30–40% до 10 минут.
12. **Кэш.** OOF и test-прогнозы сохранять на диск (`.npy`), чтобы проверять средние моделей без переобучения.

## Правила аудита
| Можно | Нельзя |
|---|---|
| Логарифмирование, винсоризация, инженерные признаки, target encoding (out-of-fold) | Признаки из порядка Id и других артефактов подготовки файлов |
| LightGBM, XGBoost, CatBoost, линейные модели, RF/ExtraTrees, kNN | Стекинг и подбор весов смеси |
| Простое (равновесное) среднее моделей, усреднение по seed. Состав смеси можно выбирать жадно по OOF, веса равные | Нейросети |
| Optuna и SHAP с пояснением (Optuna — только если укладывается по времени) | Ручная подстановка цены дубля после прогноза |
| Общие внешние данные (карта координат, открытый датасет с GitHub) — после согласования | Узкоспециальные внешние данные |

## Итоговая папка проекта
1. `data/` — исходные файлы конкурса.
2. `imports/` с `README.md` — внешние файлы, только если реально используются. Лучше обходиться без них.
3. `solution.ipynb` — единственная тетрадь для проверяющего. Вся работа от сырых данных до сабмита, оценка, короткие идейные комментарии на русском. Выполняется с нуля не дольше 10 минут в GitHub Actions (workflow `run-notebook`).
4. `REPORT.md` — тезисный человекочитаемый отчёт: методы и причины выбора, что проверено и не вошло. Без воды.
5. `service/` — служебные тетради, которые создают файлы в `imports/` (только если такие файлы есть).
6. `submissions/submission.csv`, `requirements.txt`.

Черновые эксперименты в репозиторий в итоге не попадают. Корневой `README.md` — краткая выжимка по всем проектам, пишется в самом конце.
