# Рабочие договорённости по репозиторию kaggle-pro

Четыре соревновательные задачи: `01_moscow_flat_prices`, `02_company_bankruptcy`, `03_hospital_procurement_fraud`, `04_procurement_winner`. Работаем только в ветке `main`, коммиты сразу туда.

## Роли и порядок работы
- Пользователь — аудитор. Он решает, какие методы и данные допустимы. Реализация, варианты и деление на фазы и шаги — на Claude.
- Вопросы задаются в любой момент, в том числе пока считается код. Каждый вопрос явно выделен: кратко проблема, варианты, рекомендация.
- Обязательно выносить на обсуждение:
  1. методы, допустимость которых под вопросом;
  2. любой новый импорт в тетрадь, кроме исходных данных: данные из интернета, файлы из других тетрадей.
- Решения должны быть идейными, как у исследователя, а не перебором ради метрики. Цель — минимальная ошибка.

## Скорость
- **Параллельные агенты.** Независимые направления запускать одновременно: поиск в интернете, разные семейства признаков, разные модели. Пример — Workflow `flat-prices-improve` в проекте 1.
- **Общая обвязка.** Агенты используют общий модуль с данными, фиксированными фолдами и функцией CV. На 4 CPU каждому агенту задаётся `n_jobs=2`.
- **Скрининг дешёвой моделью.** Гипотезы проверять на облегчённых настройках: большой шаг, мало деревьев, подвыборка 10–20%. В полной силе перепроверять только перспективное.
- **Подвыборки обманывают** там, где качество держится на группах. Например, «дома» квартир: на подвыборке у каждой квартиры меньше соседей. Такие идеи перепроверять на всей выборке.
- **Кэш.** OOF-прогнозы сохранять на диск, чтобы проверять средние моделей без переобучения.

## Правила аудита
| Можно | Нельзя |
|---|---|
| Логарифмирование, винсоризация, инженерные признаки, target encoding (out-of-fold) | Признаки из порядка Id и других артефактов подготовки файлов |
| LightGBM, XGBoost, CatBoost, линейные модели, RF/ExtraTrees, kNN | Стекинг и подбор весов смеси |
| Простое (равновесное) среднее моделей, усреднение по seed | Нейросети |
| Optuna и SHAP с пояснением (Optuna — только если укладывается по времени) | Ручная подстановка цены дубля после прогноза |
| Общие внешние данные (карта координат, открытый датасет с GitHub) — после согласования | Узкоспециальные внешние данные |

## Итоговая папка проекта
1. `data/` — исходные файлы конкурса.
2. `imports/` с `README.md` — внешние файлы, только если реально используются. Лучше обходиться без них.
3. `solution.ipynb` — единственная тетрадь для проверяющего. Вся работа от сырых данных до сабмита, оценка, короткие идейные комментарии на русском. Выполняется с нуля не дольше 10 минут в GitHub Actions (workflow `run-notebook`).
4. `REPORT.md` — тезисный человекочитаемый отчёт: методы и причины выбора, что проверено и не вошло. Без воды.
5. `service/` — служебные тетради, которые создают файлы в `imports/` (только если такие файлы есть).
6. `submissions/submission.csv`, `requirements.txt`.

Черновые эксперименты в репозиторий в итоге не попадают. Корневой `README.md` — краткая выжимка по всем проектам, пишется в самом конце.
